# 易程智策确定性规划基线与消融

## 1. 这份证据回答什么

本基准用于回答两个可由代码直接验证的问题：

1. 校园约束排程是否比“按输入顺序塞入最早空档”的通用日历策略更能
   生成可执行计划；
2. 在已经满足硬约束的前提下，旧计划位移成本是否确实减少了无关任务
   被重排的情况。

它不是用户调研，也不调用大模型，不把合成场景包装成真人试用结果。
输出只表示冻结输入下确定性算法的行为。

## 2. 冻结数据与可复现条件

- 数据文件：`tests/fixtures/planning_benchmark_cases.json`
- 数据版本：`2026.07.29-v1`
- 场景数：24（12个首次规划、12个事件驱动重排）
- 固定随机种子：`20260729`
- SHA256：
  `ee8a013111212982d83080c94a43b69377b3e053eb7aeb0147414da748356e5f`
- 外部网络调用：0
- 大模型调用：0
- 地图和天气实时调用：0

运行器会在解析数据前校验 SHA256。数据内容被修改但代码中的预期哈希
没有同步更新时，基准会直接失败，避免不同人拿不同测试集生成同名结果。
随机种子目前不会改变确定性排程；保留该字段是为了以后增加固定抽样时仍能
复现。

## 3. 三组算法

### 3.1 `greedy_first_fit`

这是公开、可读的通用日历基线：

- 按 JSON 中的任务输入顺序处理；
- 固定任务保持原时间；
- 可移动任务进入最早的五分钟粒度非重叠空档；
- 处理最早开始、最晚结束和截止时间；
- 不读取路线、场馆开放时间、活动有效时段、天气、依赖关系或旧计划。

该边界是为了模拟“只有空闲时间表，没有校园上下文”的最小基线。它并不
代表某个商业日历或某个大模型的真实表现。

### 3.2 `constraint_scheduler_no_history`

直接使用项目当前 `Scheduler` 和 `PlanValidator`，处理路线、通行高峰、
开放时段、天气、依赖、截止时间和固定任务；在12个重排场景中故意不把
旧计划交给候选评分。这是“关闭最小扰动目标”的消融组。

### 3.3 `constraint_scheduler_min_disruption`

首次规划使用当前 `Scheduler`，重排使用当前 `Replanner`：

- 所有候选仍必须通过相同的确定性硬约束检查；
- 旧计划开始时间进入候选位移成本；
- 锁定任务保持不动；
- 只有冲突或新约束实际影响的任务需要改变。

这就是当前完整策略。

## 4. 指标定义

| 指标 | 可复查定义 |
|---|---|
| 可行完成率 | 全部请求任务均进入计划，且硬约束违反为0的场景数 / 总场景数 |
| 硬约束违反 | `PlanValidator` 的 error 级问题，加上显式任务依赖顺序违反 |
| 截止满足率 | 已排入且结束时间不晚于 deadline 的截止任务数 / 截止任务总数 |
| 保留率 | 重排后开始时间与旧计划完全一致的旧任务数 / 新旧计划可比较任务数 |
| 误移动率 | 标注为 `unaffected_task_ids` 却被移动或删除的任务数 / 无关任务总数 |
| 总位移 | 所有仍被排入的可比较任务，开始时间绝对变化分钟数之和 |

`unaffected_task_ids` 逐案例写在冻结 JSON 中，只包含在新约束下原时段仍
应保留的任务。因此，误移动率和一般的移动率是两个不同指标：受天气、
临时课程或新依赖真实影响的任务移动，不算误移动。

## 5. 当前冻结结果

| 方法 | 可行完成率 | 硬约束违反 | 截止满足率 | 保留率 | 误移动率 | 总位移 |
|---|---:|---:|---:|---:|---:|---:|
| 贪心最早插入 | 33.3% | 19 | 50.0% | 2.8% | 95.5% | 9755分钟 |
| 约束排程（关闭历史） | 100.0% | 0 | 100.0% | 2.8% | 95.5% | 9155分钟 |
| 完整策略（最小扰动） | 100.0% | 0 | 100.0% | 72.2% | 0.0% | 1035分钟 |

这组消融支持两个有限但清晰的结论：

1. 从贪心基线到约束排程，可行完成率、硬约束和截止满足率同时改善；
2. 在两组约束排程均保持24/24可行、0硬约束违反的情况下，启用旧计划
   历史后，22个明确无关任务全部保持原时段，总位移也明显下降。

完整策略的保留率不是100%，因为冻结集中包含临时加课、开放时间推迟、
降雨、路线耗时变化和新增依赖；这些案例本来就要求受影响任务移动。

## 6. 运行和验收

从仓库根目录运行：

```powershell
& D:\APP\Dev\Python\envs\yicheng-agent\Scripts\python.exe `
  -m scripts.run_planning_benchmark
& D:\APP\Dev\Python\envs\yicheng-agent\Scripts\python.exe `
  -m pytest tests/unit/test_planning_benchmark.py
```

默认生成：

- `reports/planning_benchmark.json`：机器可读的逐案例时间与指标；
- `reports/planning_benchmark.md`：可交给材料同学复核的表格报告。

单元测试会检查：

- 冻结集恰好包含24个唯一场景，种子和 SHA256 不变；
- 连续运行两次得到完全相同的数据结构；
- 完整策略24/24可行、0硬约束违反、截止满足率100%；
- 最小扰动组相对关闭历史组提高保留率、降低误移动率和总位移；
- JSON 和 Markdown 均可生成且包含证据边界说明。

如确需更新冻结集，先审查 JSON diff，再计算新哈希：

```powershell
Get-FileHash -Algorithm SHA256 `
  tests/fixtures/planning_benchmark_cases.json
```

随后在同一个变更中更新
`scripts/run_planning_benchmark.py` 的 `EXPECTED_FIXTURE_SHA256`、本文档
以及有意改变的验收断言。不能只替换哈希来掩盖结果退化。

## 7. 使用边界

- 可以表述为“24个冻结确定性场景中，完整策略可行完成率100%、硬约束
  违反0，且22个明确无关任务误移动0”。
- 不应表述为“真实学生满意率100%”“线上模型准确率100%”或“覆盖所有
  校园场景”。
- 这份证据适合技术答辩中的基线和消融页；公网部署、真实接口稳定性、
  用户价值仍需由其他验收材料分别证明。
