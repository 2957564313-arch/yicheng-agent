### 0.1 可行性结论

在“实际投入不足一个月”的前提下，新版可以完成，但只能按比赛 MVP 交付：

- 一个面向校园日程规划的**单智能体状态图**，不做多智能体协商；
- 一个 FastAPI 后端；
- 一个轻量单页 Console；
- 5 个固定节点：需求解析、上下文补全、规划、校验、回答；
- 校园静态数据优先，地图与天气 API 作为增强能力；
- 一个“规划—校验—最多两次重规划”的闭环；
- 三个可离线复现的 Demo；
- SQLite 保存会话、计划、运行记录；
- 测试数据和指标能自动统计。

如果冻结上述范围，预计需要 **10～14 个有效开发日**，另留 3～5 天做测试、部署、PPT 和演示视频。若同时开发完整用户系统、复杂地图、后台提醒、长期画像、多智能体、OR-Tools、独立移动端或实时校园数据，计划不可控。

### 0.2 当前方案的优点

- 产品问题明确：大学生多任务、跨地点、突发变化下的日程规划；
- 参考材料已经梳理出需求解析、优先级、路线、日程、提醒和突发调整等核心业务方向；

## 1. 项目定位与边界

### 1.1 对外叙述

建议统一使用以下表述：

> 易程智策是一款面向大学生学习生活的校园时空规划智能体。系统能够理解课程、自习、取快递、用餐、运动等口语化需求，结合校园地点、开放时间、通勤和天气信息生成可执行日程，并在突发变化发生时进行局部调整。

对外不强调：

- “新版采用了多个独立智能体协作”（除非后续真的实现）；
- “LangGraph 是项目的创新点”；
- “所有路线和天气数据均为实时数据”（除非实测且没有降级）。

### 1.2 新版产品主线

项目宣传主线仍然是：

> 理解学生需求，融合校园信息，完成时空联合规划，并在计划发生变化时做最小扰动调整。

LangGraph、FastAPI、模型供应商和 RAG 只在技术实现页出现，不进入作品主标题。

### 1.3 MVP 必做

- 口语化任务解析；
- 固定任务与可移动任务区分；
- 时间、地点、时长、DDL、偏好和锁定项提取；
- 校园地点标准化；
- 静态通勤时间查询；
- 基础开放时间与规则查询；
- 简单启发式排程；
- 时间重叠、通勤不足、DDL、开放时间、任务遗漏校验；
- 最多两轮重规划；
- 突发事件下最小扰动调整；
- 结构化结果和自然语言解释；
- 单页 Console；
- 三个 Demo fixture；
- 自动化测试和评估报告；
- 应用入口、测试说明和健康检查。

### 1.4 本版不做

- 多智能体互相讨论；
- 强化学习；
- 自动学习用户行为；
- 后台常驻提醒和消息推送；
- 教务系统真实写入；
- 食堂人流、图书馆座位等实时数据；
- 完整权限系统；
- 原生 App 或小程序；
- 交互式地图导航；
- 自建大模型；
- 复杂 OR-Tools 求解；
- 全国校园通用化；
- 平台兼容层或转换工具。

```text

│ 单页 Console                                  │
│ 输入区｜Demo 按钮｜日程时间线｜风险提示｜证据  │
└──────────────────────┬───────────────────────┘
                       │ HTTP/JSON
┌──────────────────────▼───────────────────────┐
│ FastAPI                                      │
│ 请求校验｜trace_id｜统一错误｜健康检查        │
└──────────────────────┬───────────────────────┘
                       │
┌──────────────────────▼───────────────────────┐
│ LangGraph 单状态图                            │
│                                              │
│ understand → enrich → plan → validate        │
│                            ↑       │          │
│                            └──失败─┘          │
│                                    ↓通过     │
│                                  respond     │
└─────────────┬──────────────┬─────────────────┘
              │              │
┌─────────────▼──────┐ ┌─────▼────────────────┐
│ 确定性能力          │ │ 外部/知识能力         │
│ Python 排程与校验   │ │ 校园静态数据          │
│ 最小扰动重规划      │ │ 轻量 RAG              │
│ 方案评分            │ │ 地图/天气 API（可选） │
└─────────────┬──────┘ └─────┬────────────────┘
              └────────┬─────┘
┌──────────────────────▼───────────────────────┐
│ SQLite                                      │
│ 业务数据 app.db｜checkpoint checkpoint.db    │
└──────────────────────────────────────────────┘
```

### 2.1 关键工程原则

1. **LLM 负责理解和表达，不负责精确算时间。**
2. **Python 负责排序、排程、校验和最小扰动。**
3. **结构化数据优先于 RAG，RAG 优先于模型常识。**
4. **实时 API 只能增强，不能成为核心 Demo 的单点故障。**
5. **每个节点只返回 State 的局部更新，不原地修改 State。**
6. **所有持久化状态必须可 JSON 序列化。**
7. **同一输入在关闭实时数据后应得到满足相同硬约束的结果。**
8. **重规划最多两轮，失败后输出可解释的不可行原因，不无限循环。**

| 最终展示 | `respond` 节点 | 模板优先，LLM 增强 | 是 |

## 5. 核心数据模型

实现时使用 Pydantic 作为 API/领域模型，LangGraph State 使用只含 JSON 基本类型的 `TypedDict`。数据库中的 JSON 字段使用 `model_dump(mode="json")` 后写入。

### 5.1 枚举

```python
from enum import StrEnum


class Intent(StrEnum):
    PLAN = "plan"
    REPLAN = "replan"
    QUERY = "query"


class TaskFlexibility(StrEnum):
    FIXED = "fixed"
    MOVABLE = "movable"
    LOCKED = "locked"


class PlanStatus(StrEnum):
    DRAFT = "draft"
    VALID = "valid"
    INFEASIBLE = "infeasible"


class DataSource(StrEnum):
    USER = "user"
    STRUCTURED = "structured"
    LIVE_API = "live_api"
    CACHE = "cache"
    RAG = "rag"
    ESTIMATED = "estimated"
    UNKNOWN = "unknown"
```

### 5.2 Task

```python
class Task(BaseModel):
    id: str
    title: str
    date: date
    duration_min: int = Field(ge=5, le=720)

    location_id: str | None = None
    location_raw: str | None = None

    earliest_start: datetime | None = None
    latest_end: datetime | None = None
    fixed_start: datetime | None = None
    fixed_end: datetime | None = None
    deadline: datetime | None = None

    flexibility: TaskFlexibility = TaskFlexibility.MOVABLE
    importance: int = Field(default=3, ge=1, le=5)
    preferred_period: str | None = None
    depends_on: list[str] = Field(default_factory=list)
    tags: list[str] = Field(default_factory=list)
    notes: str | None = None
```

约束：

- `fixed` 或 `locked` 任务必须有 `fixed_start` 和 `fixed_end`；
- `fixed_end - fixed_start` 应与 `duration_min` 一致，允许 1 分钟舍入误差；
- `deadline` 不得早于 `earliest_start`；
- `location_raw` 保留用户原文，`location_id` 是标准化结果；
- 解析不确定时不擅自制造精确时间，写入 `clarifications`。

### 6.1 State 写入责任

| 字段 | 唯一主要写入者 |
|---|---|
| `intent/tasks/preferences/clarifications/parse_confidence` | `understand` |
| `normalized_locations/travel_estimates/weather_context/retrieved_facts/provider_warnings` | `enrich` |
| `candidate_plan/planner_diagnostics/replan_count` | `plan` |
| `validation_issues/status` | `validate` |
| `final_answer/final_plan/response_warnings` | `respond` |

各节点可以向 `node_trace` 追加一条简短记录，但不得写入 API Key、完整 Prompt、原始模型思维过程或敏感信息。

### 6.2 条件路由

```python
def route_after_understand(state):
    if state["clarifications"]:
        return "respond"
    return "enrich"


def route_after_validate(state):
    has_errors = any(
        issue["severity"] == "error"
        for issue in state["validation_issues"]
    )
    if not has_errors:
        return "respond"
    if state["replan_count"] < state["max_replans"]:
        return "plan"
    return "respond"
```

### 6.3 持久化建议

- 开发与比赛演示使用 SQLite checkpointer；
- `thread_id` 必须来自 API 请求或后端生成；
- LangGraph checkpoint 使用独立的 `runtime/checkpoints.db`；
- 业务表使用 `runtime/app.db`；
- 不把完整知识文档或大型检索结果写入 State，只保存引用和摘要；
- 关闭长期记忆宣传，除非跨 thread 的用户偏好已被明确实现和测试。

## 8. 五个节点的职责与伪代码

### 8.1 Node 1：`understand`

职责：

- 判断 `plan/replan/query`；
- 从自然语言提取任务、日期、时间、地点、时长、DDL、偏好、锁定项；
- 保留用户原始地点文本；
- 发现会显著改变方案的缺失信息；
- 输出经过 Pydantic 校验的结构化对象；
- 不计算路线、不生成最终日程。

伪代码：

```python
async def understand(state, llm):
    prompt = load_prompt("understand.md")
    raw = await llm.with_structured_output(UnderstandResult).ainvoke(
        {
            "prompt": prompt,
            "query": state["query"],
            "now": state["now_iso"],
            "timezone": state["timezone"],
            "old_plan_id": state.get("old_plan_id"),
        }
    )

    result = UnderstandResult.model_validate(raw)
    result = normalize_relative_dates(result, state["now_iso"])
    clarifications = find_blocking_missing_fields(result)

    return {
        "intent": result.intent,
        "requested_date": result.requested_date.isoformat(),
        "tasks": dump_json(result.tasks),
        "preferences": dump_json(result.preferences),
        "clarifications": clarifications,
        "parse_confidence": result.confidence,
        "status": "needs_clarification" if clarifications else "understood",
        "node_trace": [trace("understand", result.summary())],
    }
```

失败处理：

1. 首次结构化输出校验失败：将 Pydantic 错误反馈给模型，只重试一次；
2. 第二次失败：返回 `LLM_OUTPUT_INVALID`；
3. 相对日期必须基于请求中的 `now`，不得使用服务器隐含日期；
4. 不确定“下午”“晚上”的具体边界时使用配置默认值并在结果中标注。

### 8.2 Node 2：`enrich`

职责：

- 地点别名标准化；
- 获取任务地点的开放时间和校园规则；
- 计算可能相邻任务的通勤估计；
- 按需查询天气；
- RAG 只补充非结构化规则和说明；
- 标注所有事实的来源、置信度和新鲜度；
- 不决定最终任务顺序。

伪代码：

```python
async def enrich(state, providers):
    locations = {}
    warnings = []

    for task in state["tasks"]:
        resolved = providers.locations.resolve(task.get("location_raw"))
        if resolved:
            task["location_id"] = resolved.id
            locations[resolved.id] = resolved.model_dump(mode="json")
        elif task.get("location_raw"):
            warnings.append(issue("UNKNOWN_LOCATION", task["id"]))

    facts = providers.structured_rules.lookup(state["tasks"])

    # 只为候选地点对取路线，不做所有地点的 O(n²) 无限查询
    pairs = build_required_route_pairs(state["tasks"])
    routes = []
    for origin, destination in pairs:
        routes.append(
            await providers.route.get_with_fallback(
                origin, destination, mode="walk"
            )
        )

    weather = await providers.weather.get_with_fallback(
        date=state["requested_date"],
        location_id="campus_main",
    )

    rag_queries = build_rag_queries_for_missing_facts(
        tasks=state["tasks"],
        structured_facts=facts,
    )
    rag_facts = await providers.rag.retrieve(rag_queries, top_k=3)

    return {
        "tasks": state["tasks"],
        "normalized_locations": locations,
        "travel_estimates": dump_json(routes),
        "weather_context": dump_json(weather),
        "retrieved_facts": dump_json([*facts, *rag_facts]),
        "provider_warnings": dump_json(warnings),
        "status": "enriched",
        "node_trace": [trace("enrich", source_counts(...))],
    }
```

### 8.3 Node 3：`plan`

职责：

- 集中实现优先级、日程生成和突发调整；
- 固定任务先放入时间轴；
- 按优先级为可移动任务寻找可行空档；
- 加入通勤和缓冲；
- 遵守 DDL 和开放时间；
- 重规划时锁定已完成、固定和用户指定不变的任务；
- 根据上一轮 `validation_issues` 做定向修正；
- 生成候选计划，不判断最终合法性。

建议优先级评分：

```text
score =
  30 × importance_normalized
+ 25 × fixed_or_locked
+ 20 × deadline_urgency
+ 15 × dependency_urgency
+ 10 × user_preference_match
```

最小扰动代价：

```text
cost =
  1000 × cancelled_task_count
+ 100  × moved_task_count
+ 1    × total_shift_minutes
+ 0.5  × travel_minutes
+ 50   × new_warning_count
```

伪代码：

```python
def plan(state, scheduler, replanner):
    old_plan = load_old_plan_if_needed(state.get("old_plan_id"))
    issues = parse_issues(state.get("validation_issues", []))

    if state["intent"] == "replan" or state["replan_count"] > 0:
        candidate = replanner.replan(
            old_plan=old_plan or state.get("candidate_plan"),
            tasks=parse_tasks(state["tasks"]),
            context=build_planning_context(state),
            issues=issues,
            locked_task_ids=get_locked_tasks(state, old_plan),
        )
        replan_count = state["replan_count"] + 1
    else:
        candidate = scheduler.schedule(
            tasks=parse_tasks(state["tasks"]),
            context=build_planning_context(state),
        )
        replan_count = state["replan_count"]

    return {
        "candidate_plan": candidate.model_dump(mode="json"),
        "replan_count": replan_count,
        "planner_diagnostics": scheduler.last_diagnostics(),
        "status": "planned",
        "node_trace": [trace("plan", candidate.metrics)],
    }
```

排程算法第一版：

1. 构造当天可用时间窗；
2. 插入固定/锁定任务；
3. 按优先级对可移动任务排序；
4. 枚举可容纳“前通勤 + 任务 + 后缓冲”的空档；
5. 排除超 DDL、闭馆或依赖未满足的候选；
6. 对候选计算通勤、偏好、紧凑度和扰动代价；
7. 选择最低代价位置；
8. 找不到位置则保留为未排任务，不偷偷删除；
9. 生成诊断信息交给校验节点。

### 8.4 Node 4：`validate`

职责：

- 完全确定性；
- 验证时间顺序、重叠、通勤、DDL、开放时间、任务覆盖和锁定项；
- 计算实际指标；
- 生成可用于下一轮规划的机器可读 Issue；
- 不用 LLM；
- 不直接修改计划。

伪代码：

```python
def validate(state, validator):
    plan = Plan.model_validate(state["candidate_plan"])
    issues = []

    issues += validator.check_schema(plan)
    issues += validator.check_overlaps(plan)
    issues += validator.check_travel_time(
        plan, state["travel_estimates"]
    )
    issues += validator.check_deadlines(plan, state["tasks"])
    issues += validator.check_opening_hours(
        plan, state["retrieved_facts"]
    )
    issues += validator.check_task_coverage(plan, state["tasks"])
    issues += validator.check_locked_tasks(
        plan, state.get("old_plan_id"), state["preferences"]
    )

    metrics = validator.calculate_metrics(plan, issues)
    plan.metrics = metrics
    plan.status = (
        PlanStatus.VALID
        if not has_error(issues)
        else PlanStatus.INFEASIBLE
    )

    return {
        "candidate_plan": plan.model_dump(mode="json"),
        "validation_issues": dump_json(issues),
        "status": "valid" if plan.status == "valid" else "invalid",
        "node_trace": [trace("validate", metrics)],
    }
```

### 8.5 Node 5：`respond`

职责：

- 在需要澄清时只提出最少问题；
- 在成功时输出易读日程、路线、提醒和调整原因；
- 在超过重规划次数时明确说明无法满足哪些约束；
- 保留结构化 `Plan` 供前端渲染；
- 不重新计算时间或偷偷改变计划；
- LLM 失败时使用模板输出。

伪代码：

```python
async def respond(state, llm, templates):
    if state["clarifications"]:
        answer = templates.clarification(state["clarifications"])
        return {
            "final_answer": answer,
            "final_plan": None,
            "response_warnings": state.get("provider_warnings", []),
            "status": "needs_clarification",
        }

    plan = Plan.model_validate(state["candidate_plan"])
    all_warnings = [
        *state.get("provider_warnings", []),
        *state.get("validation_issues", []),
    ]

    if has_error(all_warnings):
        answer = templates.infeasible(plan, all_warnings)
    else:
        try:
            answer = await llm.generate_from_frozen_plan(
                plan=plan,
                facts=state["retrieved_facts"],
                warnings=all_warnings,
            )
            assert_plan_times_unchanged(answer, plan)
        except Exception:
            answer = templates.success(plan, all_warnings)

    save_plan_and_run(...)
    return {
        "final_answer": answer,
        "final_plan": plan.model_dump(mode="json"),
        "response_warnings": all_warnings,
        "status": "completed" if not has_error(all_warnings) else "partial",
        "node_trace": [trace("respond", {"template_fallback": ...})],
    }
```

## 11. 地图与天气降级策略

### 11.1 路线数据降级链

按以下顺序执行：

1. **静态已核验路线表**：校园 Demo 默认首选，速度快、稳定；
2. **实时地图 API**：仅在 `mode=live` 或静态无数据时调用；
3. **坐标直线距离估算**：按 `distance × 1.25 / walking_speed` 估算；
4. **同区域默认值**：仅对已知同一校园区域使用；
5. **未知**：返回 `UNKNOWN_LOCATION` 或 `API_DEGRADED`，不得编造精确距离。

实时 API 建议：

- 连接超时 1.5 秒；
- 总超时 3 秒；
- 最多重试 1 次；
- 只对幂等请求重试；
- 缓存成功结果；
- 记录供应商、请求耗时和降级级别；
- 不在日志中记录 Key。

### 11.2 天气数据降级链

1. 实时天气/预报 API；
2. 同地点、同预报周期且未过期的缓存；
3. Demo fixture（仅 `/demos/*` 离线模式）；
4. `unknown`。

天气未知时：

- 继续排程；
- 不自动取消或改动户外任务；
- 输出“未获取到可靠天气，户外安排请出发前确认”；
- 不显示虚构的降雨概率或温度。

### 11.3 供应商接口

```python
class RouteProvider(Protocol):
    async def get_route(
        self,
        origin_id: str,
        destination_id: str,
        mode: str,
    ) -> TravelEstimate: ...


class WeatherProvider(Protocol):
    async def get_forecast(
        self,
        date: date,
        location_id: str,
    ) -> list[WeatherContext]: ...
```

节点只能依赖协议，不得直接绑定高德或具体天气供应商。

## 12. RAG 的优先级与范围

### 12.1 信息优先级

发生冲突时按以下优先级：

1. 用户本轮明确约束；
2. 结构化校园事实：地点、开放时间、静态路线、校历；
3. 可验证的实时 API；
4. 带来源和更新时间的 RAG 文档；
5. 用户显式偏好；
6. LLM 常识推断。

硬规则不得被 LLM 的“更合理建议”覆盖。

### 12.2 RAG 只处理

- 场馆和服务说明；
- 校园办事流程；
- 使用规则；
- 校历或作息说明；
- 地点文字介绍；
- 无法方便结构化的校园 FAQ。

### 12.3 RAG 不处理

- 精确距离和通勤时间；
- 实时天气；
- 时间加减；
- 时间冲突；
- DDL 判断；
- 任务优先级计算；
- 最终日程求解；
- 用户锁定项。

### 12.4 一个月内的实现优先级

第一版先做：

- Markdown 文档；
- 每篇文档带 front matter：`source_url`、`verified_at`、`applies_to`、`priority`；
- 关键词/BM25 或简单向量检索二选一；
- `top_k=3`；
- 检索结果必须返回文档 ID、片段和来源；
- 没检索到就返回空，不让模型自行补全校园事实。

只有 30 条评估问题中，关键词检索无法覆盖超过 20% 时，才增加向量数据库。比赛版不为了“技术栈丰富”强制上 Chroma/FAISS。

| 降级成功率 | 供应商失败后仍返回可用计划的案例 / 降级案例数 |

## 18. 风险登记

| 风险 | 概率 | 影响 | 预防 | 兜底 |
|---|---|---|---|---|
| 输入材料存在缺页或保存网页缺少原文 | 中 | 中 | 只导入可提取正文 | 跳过并记录原因，不猜测内容 |
| 模型 JSON 不稳定 | 中 | 高 | 结构化输出、Pydantic、一次修复 | 返回澄清/模板，不继续瞎排 |
| 地图 API 申请或调用失败 | 高 | 中 | 静态路线表优先 | 估算并标注来源 |
| 天气 API 失败 | 高 | 低 | 缓存和超时 | unknown，不阻断 |
| 校内地点无法被地图识别 | 高 | 中 | 自建地点 ID 和 alias | 人工核验 20～30 个地点 |
| 排程算法出现边界错误 | 中 | 高 | 单元测试和确定性 validator | 明确不可行，不输出冲突方案 |
| LangGraph 循环失控 | 低 | 高 | `max_replans=2` | 停止并输出问题 |
| SQLite 锁冲突 | 低 | 中 | WAL、短事务、连接管理 | 单进程演示，减少并发 |
| RAG 与结构化事实冲突 | 中 | 高 | 固定优先级 | 忽略低优先级 RAG 结果 |
| 开放时间过期 | 中 | 中 | `verified_at` 和有效期 | UI 标注需复核 |
| 过度开发前端 | 中 | 中 | 单页 Console 冻结 | 删除动画、地图、注册 |
| 团队把目标改回多智能体 | 中 | 高 | 冻结规则 | 赛后路线，不进当前分支 |
| 部署现场网络不稳定 | 高 | 高 | 离线 fixture | 本地运行 + 演示视频 |
| PPT 功能超出实际实现 | 中 | 高 | 功能清单逐项核验 | 未实现项移到未来规划 |
| Codex 一次改动过大 | 高 | 高 | 按 Task 00～13 分步 | 回退该任务，不重置用户改动 |

## 22. 最终验收口径

项目完成不是“代码能启动”，而是满足以下用户结果：

1. 学生输入一段自然语言，系统能识别任务与关键约束；
2. 系统能基于校园地点、开放时间和通勤生成一份无硬冲突计划；
3. 突发变化发生时，系统能保持用户锁定任务并做局部调整；
4. 地图或天气失败时，系统不会整体崩溃，也不会伪造实时信息；
5. 用户能在一个网页里看懂时间线、路线、风险和调整原因；
6. 三个 Demo 可离线复现；
7. 测试结果能由脚本重新生成；
8. 项目材料中的功能、测试数字与当前实际实现保持一致。
