# 关键工程决策

## 1. 比赛版只有五个状态节点

固定为 `understand → enrich → plan → validate → respond`。路线、天气、
RAG、排程器和校验器是能力模块，不拆成互相对话的多个智能体。

## 2. 大模型不负责精确排程

模型只用于自然语言理解和结果表达。日期计算、时间冲突、截止时间、开放
时间、通勤和最小扰动由 Python 确定性逻辑负责。

## 时间约束与通勤

时间约束是规划器的最高优先级。用户明确的课程节次、固定起止时间、
最早开始、最晚结束和截止时间均作为硬约束；个人偏好、路线成本和错峰
意愿只能在硬约束允许的范围内优化。

默认通勤方式为步行。在线模式按用户本轮表达选择高德步行、骑行或
电动车路径规划接口。高德返回值作为基础通勤时间；若实际出发时刻落入
校园集中通行窗口，系统额外加入结构化高峰缓冲并重新校验后续任务。
高峰期允许通行，系统只提醒并提供可选错峰方案，不强制改变用户安排。

## 3. 离线能力是第一优先级

地图、天气和模型都是可选增强。外部服务不可用时，系统必须给出明确提示，
并在可用静态数据范围内继续规划。

## 4. RAG 不覆盖结构化硬约束

开放时间、地点坐标、通勤矩阵等硬约束必须来自已核验结构化数据。知识库
用于检索说明、规则原文和校园服务信息，发生冲突时按数据优先级处理。

## 5. 不伪造校园事实

附件未导入、坐标未核验、来源日期不清楚的内容一律标记为演示数据或
`verified: false`。比赛版可以展示机制，但不能把测试 fixture 当成正式事实。

## 6. 当前数据库只支持单实例

SQLite 便于短周期开发和演示。若后续需要多人并发、后台任务或多实例部署，
再迁移 PostgreSQL；本轮不提前引入额外运维复杂度。

## 7. 冻结规则

进入提交前 7 天后，只允许：

- 修复 P0/P1 缺陷；
- 补真实数据和来源；
- 提升测试覆盖；
- 优化不改变接口契约的文案与样式。

禁止新增框架、多智能体、完整注册/找回密码系统、交互地图、后台推送和
未经验证的实时数据源。比赛测试账号的轻量登录不属于完整用户系统。
